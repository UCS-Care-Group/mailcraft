# Where MailCraft falls short of Outlook

> **Last reviewed:** 2026-10-15 · **Last updated:** 2026-10-17 · **Change:** minor (gap 5: shared mailboxes, being tested behind a switch, send mail from their own address, their drafts kept in their own Drafts, #70; gap 5: shared mailboxes, being tested behind a switch, send their changes up to their own address, deleted mail to their own Deleted Items, #70; gap 5: shared mailboxes, being tested behind a switch, are read, searched, counted and can be Favorites, #70; gap 8: the first save after a large download is written in the background, and nothing the window does waits for it, R6.3; gap 8: attachments and older bodies stay on disk and are read when wanted, R6.1; gap 8: the mailbox file is a log of records a save appends to, R6; gap 18 and rough edges: told when a new version is out, never updated by itself, R7.3; gap 2 and rough edges: a Microsoft account on IMAP switches to Graph once its owner says so, R3.7, and new ones are Graph's; gap 2 and rough edges: undo after a change reached a Microsoft account's server, R3.5; rough edges: imported mail for a Microsoft account goes to a local folder, R3.6; rough edges: a refused delete for good is put back at once; rough edges: sending and held messages through Graph, R3.4.2; drafts of a Microsoft account up through Graph, R3.4.1; a refused delete for good is put back at once; gap 2 and rough edges: behind the switch for testing, a Microsoft account's mail down and message changes up through Microsoft Graph, R3.2, R3.3.2; its folders, R3.1; gap 4: sign-ins remembered on Linux and FreeBSD through the Secret Service; Exchange Web Services removed: one way of reading Outlook's Favorites; gap 7: the compose body is rich text underneath and goes out as HTML; the rich-text editor, R4.2) · **Target:** Microsoft Outlook (Microsoft 365)

Since 2026-10-14 the order of the work is the roadmap reset;
this list stays the record of what falls short. The work list. One entry per shortfall, ranked by how much it stops an Outlook user from switching
(**B** = blocks beta). Each says what's missing, the evidence, who it hurts, a rough estimate of
focused work, and which parity document tracks it. Pick from the top, check open PRs first, and
update this file and the parity doc when a gap closes. Estimates are guesses until someone has
done similar work in this code base.

## Known rough edges (small, not ranked)

- A sync that hits the per-run download cap leaves the rest for the next run without saying so.
- Server folders that disappear are not removed locally (IMAP). For an account kept in step through Graph (R3.1) they are, with their mail, after a listing that went to its end; a listing cut short removes nothing.
- R3.1 asks for `Mail.ReadWrite` (reading and changing folders through Graph) for an account kept in step through Graph, and for no other. The admin-consent list and the sign-in rule of `CLAUDE.md` don't name it yet (R3.2; the owners' decision). Immutable ids are asked for by the Graph code of mail only: calendar, contacts and sending still get Graph's ordinary ids, which is what a mailbox of 0.2.x keeps its events and contacts by.
- A mailbox the server numbers anew (a new UIDVALIDITY) keeps what was done here and not yet pushed: each change is made again on the message's new copy, found by its Message-ID, and the owner is told of any that can't be (a message without a Message-ID). A move or deletion whose message never comes back waits on, harmlessly.
- Changes of messages through Graph (R3.3.2): a refusal is written to the program's log by status and Graph's code only (there is no Send/Receive log of its own yet), and the status bar says it once per run and kind. A delete for good the server refuses is put back at once, with what was fetched of it (R3.3 follow-up). Undo keeps its history after a change reached the server and sends the reverse with the next run (R3.5); a delete for good and sending can't be undone, and the undo says so. Undo of a calendar change still forgets the history once it reached the server. Moving or copying mail into a Microsoft account from elsewhere is refused until R3.4, and so is copying out a message that isn't downloaded yet; received mail in a local folder, imported mail included, never goes in (Graph makes only drafts), and mail imported for a Microsoft account goes to the local folder Imported (R3.6). None of it has met the real service.
- Drafts through Graph (R3.4.1): a reply or forward to a message that isn't on the account's server (a local folder, another account) is made on the server as a message of its own, without `In-Reply-To` and `References` (Graph lets a program write only `x-` headers), so the server doesn't thread it; an attachment over 150 MB isn't taken up. Sending (R3.4.2) goes through Graph alone: a saved draft as that draft, a message never saved with `sendMail`; a send whose answer was lost, or that Microsoft refused, is held in the Outbox with what to check, and goes again only with Send Again. None of it has met the real service.
- The switch from IMAP to Graph (R3.7): asked once per account, on a page of its own. While anything waits for the IMAP server it waits; when the server can't be reached the owner can switch without what waits (Switch without Them), and the changes left behind stay in the backup. A mailbox not kept in a file isn't switched. What only is on this computer goes to a local folder "Kept from <address>". None of it has met the real service.
- Outlook's Favorites are read from the server for an account that signs in with Microsoft (M4.2) and never written: the list is changed in Outlook, and `folder.favorite` says so. They come from an item that Microsoft Graph documents in its beta version only, whose content nobody documents (the cached configuration of Outlook on the web), so they can stop coming without notice; MailCraft's own favourites are shown then. Reading them takes two permissions the owner is asked for separately, of which Microsoft's permissions reference says one needs an administrator in an organisation (its Graph Explorer says not): where that holds, the folder pane says that an administrator has to approve it once and offers a message to copy for them and the page that says what to do next (M4.4, below). That the page comes back with the code that says so, rather than staying open, is not proven. A favourite that is a person, a category or a group is not shown; other providers have no such list. Proven on one mailbox by hand and against a stand-in since; how soon a change made in Outlook shows in that item is not known.
- Outlook's Favorites have one way of being read, Microsoft Graph (R2). Exchange Web Services, which 0.2.0 and 0.2.1 offered as a second way for a work or school account, is gone from the program, with the choice between the two; a mailbox whose owner had chosen it, or "not now", opens, has them read through Graph from then on and says so once (an owner who would rather keep MailCraft's own turns Outlook's off in File › Options). An owner who chose Exchange Web Services because the organisation would not approve Graph's permissions sees MailCraft's own favourites until an administrator approves them.
- An organisation that lets only an administrator approve a new program (M4.4): Microsoft's sign-in page then says "Need admin approval" instead of signing the owner in. Add Account says what to do about that while the page is still open, on a page of its own, and whenever a sign-in ends without having signed anybody in (the page came back with a no, nothing came back, no browser could be started); an account that exists gets the same page when a Send/Receive its owner asked for, or what was asked for its Favorites, is refused for it. An owner who is an administrator approves on Microsoft's admin-consent page, opened from there and waited for on a loopback port; any other copies a short message for one, with that page's address. **None of this has met the real service**, and it is written from Microsoft's identity-platform documentation alone. What is least certain, most doubtful first: that the admin-consent page takes the permissions of two services (the mail servers' and Microsoft Graph's) in one request, which the documentation says of the sign-in page and not of this one (the page opened from here is asked again service by service when it comes back refused for that; the address in the message can't be); that it accepts a way back to `http://localhost` on any port, as the sign-in page does; that the organisation's directory can be named by the mail domain of the address (it is left to the administrator's own sign-in where the address is at a provider of personal mail); what comes back from "Need admin approval" when the owner leaves it (the documentation says `AADSTS65004`, "user declined", where the organisation has approval requests switched on, which is also what an owner's own no looks like, so the wizard says both and offers the page about an approval; where requests are off it says nothing, and nothing may come back at all). A sign-in with an administrator's account on Microsoft's own page brings back tokens for that account, not the owner's: the wizard takes the name that signed in as the servers' user name, as it does for an alias.
- New versions (R7.3): told of, never installed (that waits on signed releases). The check asks GitHub's API alone, so a tester behind a network that blocks `api.github.com` hears nothing, and GitHub's answer for a release with many packages has to stay within 512 KB to be read (0.4.2's is 44 KB).
- The window's caption strip is the system's, so in dark mode it is a slightly different dark than the rest; text is drawn without subpixel smoothing.
- An appointment window is one row of commands, not a ribbon with tabs; its questions about mail to attendees come up in the main window.
- Conversations are grouped by subject, so two unrelated threads with the same subject merge.
- `vcard` drops name prefixes/suffixes, photos and anniversaries; `ical` ignores `RDATE`, `BYMONTHDAY` lists and recurring to-dos.
- Undo in the window covers the mailbox; the message being written has its own (Ctrl+Z while its body has the keyboard).
- A calendar change the server says it took is checked against what comes down next, and put back with a word when the server doesn't show it; whether the real Microsoft 365 service takes every kind of change as it is sent is known only for what the owner's Check Calendar Connection (File › Info) exercises: an appointment's time, as an instant and said in a time zone.

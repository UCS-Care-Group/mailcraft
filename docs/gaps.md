# Where MailCraft falls short of Outlook

> **Last reviewed:** 2026-10-14 · **Last updated:** 2026-10-14 · **Change:** major (wave 4: gap 14 translations; wave 3: gaps 7 and 16 closed, 6, 8, 9 and 10 rewritten; wave 1: gaps 4, 11 and 13 closed; gap 15 printing closed; most of gap 17 done; gap 2 uploads drafts, copies, imports and categories and listens with IDLE; gap 2 sends folder changes; gap 5 has shared mailboxes; the IMAP download is batched) · **Target:** Microsoft Outlook (Microsoft 365)

The work list. One entry per shortfall, ranked by how much it stops an Outlook user from switching
(**B** = blocks beta). Each says what's missing, the evidence, who it hurts, a rough estimate of
focused work, and which parity document tracks it. Pick from the top, check open PRs first, and
update this file and the parity doc when a gap closes. Estimates are guesses until someone has
done similar work in this code base.

## Known rough edges (small, not ranked)

- `mailcraft-cli sync` stops at a per-run download cap (256 MB, 100,000 messages) and leaves the rest for the next run without saying so; the desktop app has no such cap.
- The IMAP download uses one connection; Exchange Online would allow two to four at once.
- Folders under Deleted Items that are not mail folders (a deleted calendar or contact list) are listed there; Outlook doesn't show them. Telling them apart over IMAP isn't reliable; reading the folder list through Microsoft Graph would, and is the owner's decision.
- Mail sent as a shared mailbox gets its server copy in the owner's own Sent Items unless an administrator sets `MessageCopyForSentAsEnabled`; Graph sending with `Mail.Send.Shared` would file it in the shared mailbox's (an owner's decision: a new permission).
- System notifications on Windows show only for the installed program (its Start Menu shortcut carries the app id).
- Outlook's Favorites are read from the server for an account that signs in with Microsoft (M4.2) and never written: the list is changed in Outlook, and `folder.favorite` says so. They come from an item that Microsoft Graph documents in its beta version only, whose content nobody documents (the cached configuration of Outlook on the web), so they can stop coming without notice; MailCraft's own favourites are shown then. Reading them takes two permissions the owner is asked for separately, of which Microsoft's permissions reference says one needs an administrator in an organisation (its Graph Explorer says not): where that holds, the folder pane says that an administrator has to approve it once and offers a message to copy for them and the page that says what to do next (M4.4, below). That the page comes back with the code that says so, rather than staying open, is not proven. A favourite that is a person, a category or a group is not shown; other providers have no such list. Proven on one mailbox by hand and against a stand-in since; how soon a change made in Outlook shows in that item is not known.
- The owner of a work or school account chooses how Outlook's Favorites are read (M4.3): Microsoft Graph as above, Exchange Web Services, or not now. **The Exchange Web Services reader has never met the real service.** It is written from the public EWS reference and the open specifications ([MS-OXOCFG], [MS-OXWSSRCH], [MS-OXWSFOLD], [MS-OXWSCDATA], [MS-OXCDATA]) and held to them by a stand-in, and reads the navigation shortcuts classic Outlook keeps, which is another list than the one Outlook on the web and the new Outlook keep (the one Graph reads): somebody who only ever used those may find it empty, and MailCraft's own favourites are shown then. What is least certain, most doubtful first: that the folder the shortcuts are in is found by the name "Common Views" in every mailbox (nothing documents how EWS finds it); that a folder's EntryID as EWS gives it is the one a shortcut names; that asking for the two group properties under both of the types the documents give them is taken (the reader asks again without them when it isn't); that an organisation which lets its people agree to applications lets them agree to this one (Microsoft's default consent policy for new organisations keeps Exchange Web Services for administrators, in which case the pane says an administrator has to approve it, as for Graph); and what a personal account is told. It stops for everybody on 1 April 2027, from when it is not offered. A personal Microsoft account has Graph only; which kind an account is, is read from the directory its sign-in names.
- An organisation that lets only an administrator approve a new program (M4.4): Microsoft's sign-in page then says "Need admin approval" instead of signing the owner in. Add Account says what to do about that while the page is still open, on a page of its own, and whenever a sign-in ends without having signed anybody in (the page came back with a no, nothing came back, no browser could be started); an account that exists gets the same page when a Send/Receive its owner asked for, or what was asked for its Favorites, is refused for it. An owner who is an administrator approves on Microsoft's admin-consent page, opened from there and waited for on a loopback port; any other copies a short message for one, with that page's address. **None of this has met the real service**, and it is written from Microsoft's identity-platform documentation alone. What is least certain, most doubtful first: that the admin-consent page takes the permissions of two services (the mail servers' and Microsoft Graph's) in one request, which the documentation says of the sign-in page and not of this one (the page opened from here is asked again service by service when it comes back refused for that; the address in the message can't be); that it accepts a way back to `http://localhost` on any port, as the sign-in page does; that the organisation's directory can be named by the mail domain of the address (it is left to the administrator's own sign-in where the address is at a provider of personal mail); what comes back from "Need admin approval" when the owner leaves it (the documentation says `AADSTS65004`, "user declined", where the organisation has approval requests switched on, which is also what an owner's own no looks like, so the wizard says both and offers the page about an approval; where requests are off it says nothing, and nothing may come back at all); and that one approval of everything keeps an earlier approval of Exchange Web Services (the documentation says a tenant-wide approval "may revoke" earlier ones, which is why the address for an account whose Favorites are set to Exchange Web Services asks for that with the rest). A sign-in with an administrator's account on Microsoft's own page brings back tokens for that account, not the owner's: the wizard takes the name that signed in as the servers' user name, as it does for an alias.
- The window's caption strip is the system's, so in dark mode it is a slightly different dark than the rest; text is drawn without subpixel smoothing.
- An appointment window is one row of commands, not a ribbon with tabs; its questions about mail to attendees come up in the main window.
- Conversations are grouped by subject, so two unrelated threads with the same subject merge.
- `vcard` drops name prefixes/suffixes, photos and anniversaries; `ical` ignores `RDATE`, `BYMONTHDAY` lists and recurring to-dos.
- Undo covers the mailbox, not the message being written.
- A calendar change the server says it took is checked against what comes down next, and put back with a word when the server doesn't show it; whether the real Microsoft 365 service takes every kind of change as it is sent is known only for what the owner's Check Calendar Connection (File › Info) exercises: an appointment's time, as an instant and said in a time zone.

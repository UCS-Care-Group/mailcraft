# Where MailCraft falls short of Outlook

> **Last reviewed:** 2026-10-20 · **Last updated:** 2026-10-26 · **Change:** patch

The ranked list of shortfalls and rough edges. The direction is in [`ROADMAP.md`](../ROADMAP.md):
where MailCraft stands, the beta checklist and the steps to it, and what comes after beta; the order
of the work to beta is the roadmap reset there, and this list stays the record of what falls short.
One entry per shortfall, ranked by how much it stops an Outlook user from switching
(**B** = blocks beta). Each says what's missing, the evidence, who it hurts, a rough estimate of
focused work, and which document tracks it: `ROADMAP.md` (the beta checklist, or after beta) or a
parity checklist. Pick from the top, check open PRs first, and update this file and the document
that tracks the gap when it closes. Estimates are guesses until someone has done similar work in
this code base.

## Known rough edges (small, not ranked)

- Slow Send/Receive on a Microsoft account with many folders, and on shared mailboxes (#276): new mail can take minutes. Send/Receive Progress now says how long each phase of each account took (under the row, and on its Done line), and Copy Diagnostics adds, per account, the time of each phase, the requests made and the folders skipped, so that the cause can be measured on a real mailbox before it is fixed; the Calendar and contacts phase is not timed yet. A Send/Receive now starts with an Inbox pass: before anything else of the run (token renewal aside), every account kept in step through Graph, the owner's and each shared mailbox, brings its Inbox's delta from its stored link, one small request each, so that new mail shows within seconds; then each account's run goes on as before, from the link the pass moved on. An account whose Inbox is known but has never been read has a pass that reads it from its start; one never listed, and a mail-server account, have none. Mail-server (IMAP) accounts still go a folder at a time with the Inbox first after the folder list, and are left for the later steps of #276. The pass is shown as the Inbox phase in Send/Receive Progress and Copy Diagnostics. The calendar and contacts no longer sit in that run: they are a job of their own after the round, so the next account's mail starts as soon as the one before has its mail in. Folders that haven't changed are skipped: one of the owner's own folders (never the Inbox or another special folder) whose message and unread counts in the folder listing are what they were when its delta last ended, and which is caught up, is passed over, and counted as skipped; a page that brings nothing new is not handed on and changes nothing in the mailbox. A change that leaves both counts as they were (a flag or category, one message in and one out) waits for a full sweep of every folder, which is the first run after the mailbox is opened, then one an hour, and any run while a message the server said left a folder waits to be removed; mail that left a folder read and turned up in none of them has the folders passed over read in the same run. Graph's requests now go on connections kept open (at most four to a server, each kept for half a minute between requests), so a run no longer opens a new secure connection for every request. The folder listing asks for the subfolders of twenty folders in one `$batch` request, a level of the tree at a time, where each folder with subfolders took a request of its own (35 requests for 332 folders on a real mailbox); a list that fails inside a batch is asked by itself, and the listing says it is incomplete when that fails too. Between rounds, every minute while the window is open, each of those accounts has its Inbox pass on its own, one after the other: only while Send/Receive runs by itself, never while a round, a sign-in or another check is under way (that minute is left out, and the next check is a minute after a round), and quietly: Send/Receive Progress and the status line don't show it, nothing is asked, and a failure goes to the log and is tried the next minute. A Send/Receive asked for during a check goes ahead at once.
- A sync that hits the per-run download cap leaves the rest for the next run without saying so.
- An HTML signature (File › Signatures) is shown in a message being written as a simpler copy in rich text, without its tables and layout; recipients get the HTML unless the owner edits that copy. Its pictures are those on the web only: a picture kept on this computer needs a rich signature.
- Server folders that disappear are not removed locally (IMAP). For an account kept in step through Graph (R3.1) they are, with their mail, after a listing that went to its end; a listing cut short removes nothing.
- R3.1 asks for `Mail.ReadWrite` (reading and changing folders through Graph) for an account kept in step through Graph, and for no other. The admin-consent list and the sign-in rule of `CLAUDE.md` don't name it yet (R3.2; the owners' decision). Immutable ids are asked for by the Graph code of mail only: calendar, contacts and sending still get Graph's ordinary ids, which is what a mailbox of 0.2.x keeps its events and contacts by.
- A mailbox the server numbers anew (a new UIDVALIDITY) keeps what was done here and not yet pushed: each change is made again on the message's new copy, found by its Message-ID, and the owner is told of any that can't be (a message without a Message-ID). A move or deletion whose message never comes back waits on, harmlessly.
- Changes of messages through Graph (R3.3.2): a refusal is written to the program's log by status and Graph's code only (there is no Send/Receive log of its own yet), and the status bar says it once per run and kind. A delete for good the server refuses is put back at once, with what was fetched of it (R3.3 follow-up). Undo keeps its history after a change reached the server and sends the reverse with the next run (R3.5); a delete for good and sending can't be undone, and the undo says so. Undo of a calendar change still forgets the history once it reached the server. Moving or copying mail into a Microsoft account from elsewhere is refused until R3.4, and so is copying out a message that isn't downloaded yet; received mail in a local folder, imported mail included, never goes in (Graph makes only drafts), and mail imported for a Microsoft account goes to the local folder Imported (R3.6). None of it has met the real service.
- Drafts through Graph (R3.4.1): a reply or forward to a message that isn't on the account's server (a local folder, another account) is made on the server as a message of its own, without `In-Reply-To` and `References` (Graph lets a program write only `x-` headers), so the server doesn't thread it; an attachment over 150 MB isn't taken up. Sending (R3.4.2) goes through Graph alone: a saved draft as that draft, a message never saved with `sendMail`; a send whose answer was lost, or that Microsoft refused, is held in the Outbox with what to check, and goes again only with Send Again. None of it has met the real service.
- Shared mailboxes (#70): the owner types the address (Microsoft offers no list of the mailboxes he may open), and each permission is asked for by itself the first time it is needed (reading at the first Send/Receive, sending at the first send), never with a sign-in. A shared mailbox's calendars are read once one is ticked in the calendar's folder list, and the owner is then asked for `Calendars.ReadWrite.Shared`, by itself (the same permission and question when the owner opens somebody's calendar by address, which is kept on this computer only and read and changed by the same code; a person who shares only free and busy times is shown as blocks); where the owner may edit one it is changed from here as his own is (items made, changed and deleted, meetings called off and forwarded, meeting requests in the mailbox answered from its address; sending from it is asked for with the question mail has), and rights that shrink hold what waits instead of dropping it. An appointment (not a meeting, a series or an item with files) can be moved between the owner's calendar and a shared mailbox's or an opened one where he may edit both, by making it at the target's own address and deleting the original at its own once the copy is seen; it is not an Undo step once the copy is made, and a copy is never taken out of another mailbox behind its owner's back. A message moved or copied between the owner's mailbox and a shared mailbox (either way, or between two of his shared mailboxes) is made in the destination by that mailbox's own Send/Receive, from the whole message here, as received mail with its times, read state, flag, categories and attachments; of a move, the original is removed from its own mailbox only once the copy is confirmed on the other server, so a copy that fails never loses it (the message goes back where its original still is, and that is said). What isn't the same as a move within one mailbox: it takes two Send/Receive runs (the destination's, then the source's); a message not downloaded yet, or a draft, is refused with the reason; the copy is a new message on the server (a new id, and the server's own record of where it came from, such as its original headers, isn't carried across); and a server that keeps what MailCraft makes as a draft has it taken away again and the move refused, which has not yet been tried against Exchange Online itself. Not to another account's mailbox: two sign-ins are two organisations' mail (#155).
- The switch from IMAP to Graph (R3.7): asked once per account, on a page of its own. While anything waits for the IMAP server it waits; when the server can't be reached the owner can switch without what waits (Switch without Them), and the changes left behind stay in the backup. A mailbox not kept in a file isn't switched. What only is on this computer goes to a local folder "Kept from <address>". None of it has met the real service.
- Outlook's Favorites are read from the server for an account that signs in with Microsoft (M4.2) and never written: the list is changed in Outlook, and `folder.favorite` says so. They come from an item that Microsoft Graph documents in its beta version only, whose content nobody documents (the cached configuration of Outlook on the web), so they can stop coming without notice; MailCraft's own favourites are shown then. Reading them takes two permissions the owner is asked for separately, of which Microsoft's permissions reference says one needs an administrator in an organisation (its Graph Explorer says not): where that holds, the folder pane says that an administrator has to approve it once and offers a message to copy for them and the page that says what to do next (M4.4, below). That the page comes back with the code that says so, rather than staying open, is not proven. A favourite that is a person, a category or a group is not shown; other providers have no such list. Proven on one mailbox by hand and against a stand-in since; how soon a change made in Outlook shows in that item is not known.
- Outlook's Favorites have one way of being read, Microsoft Graph (R2). Exchange Web Services, which 0.2.0 and 0.2.1 offered as a second way for a work or school account, is gone from the program, with the choice between the two; a mailbox whose owner had chosen it, or "not now", opens, has them read through Graph from then on and says so once (an owner who would rather keep MailCraft's own turns Outlook's off in File › Options). An owner who chose Exchange Web Services because the organisation would not approve Graph's permissions sees MailCraft's own favourites until an administrator approves them.
- An organisation that lets only an administrator approve a new program (M4.4): Microsoft's sign-in page then says "Need admin approval" instead of signing the owner in. Add Account says what to do about that while the page is still open, on a page of its own, and whenever a sign-in ends without having signed anybody in (the page came back with a no, nothing came back, no browser could be started); an account that exists gets the same page when a Send/Receive its owner asked for, or what was asked for its Favorites, is refused for it. - New versions (R7.3): told of; a copy that updates itself downloads and checks a newer one and installs it at Restart to update or at quit, and until the release keys are set (and a release is signed) it downloads nothing.

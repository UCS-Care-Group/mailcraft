# Finding an Exchange server: Autodiscover

> **Last reviewed:** 2026-11-12 · **Last updated:** 2026-11-12 · **Change:** major

When the owner sets up an Exchange server account (#252) without typing the server's address,
MailCraft looks for it from the e-mail address with Autodiscover. Two public specifications from
Microsoft describe how:

- **[MS-OXDISCO]** (Autodiscover HTTP Service Protocol) says where a client looks: the list of
  possible Autodiscover addresses, §3.1.5.
- **[MS-OXDSCLI]** (Autodiscover Publishing and Lookup Protocol) says what a client asks each of
  them and how it reads the answers and redirects, §3.1.5. It doesn't fix where the list comes
  from: it "could be generated by using the [MS-OXDISCO] protocol" and "could also be
  preconfigured" (§3.1.3).

This page says which of MS-OXDISCO's steps MailCraft takes and which it doesn't, and it
specifies the one step of MailCraft's own: **the alias step** (#1103). The code is
`crates/ews/src/autodiscover.rs` (the search, which does no I/O) and `crates/net/src/dns_srv.rs`
(the DNS questions). The rules on what is sent to whom are in
[threat-model.md](threat-model.md) › Provider discovery, and in `AGENTS.md`.

The specifications quoted are the editions of 2025: MS-OXDISCO v20250520 and MS-OXDSCLI
v20250819.

## MS-OXDISCO's steps

MS-OXDISCO §3.1.5 says a client SHOULD take four steps to fill its list, and that "a client can
acquire the URI of an Autodiscover server without a fully populated list". MailCraft's list,
in the order it is asked:

| MS-OXDISCO | The step | MailCraft |
|---|---|---|
| §3.1.5.1 | Service connection points from the organisation's LDAP directory | Not taken: MailCraft doesn't join a Windows domain or ask its directory |
| §3.1.5.2 | `<Domain>/Autodiscover/Autodiscover.xml` and `https://Autodiscover.<Domain>/Autodiscover/Autodiscover.xml` | Taken, both over HTTPS. (§3.1.5.2 writes the first with `http://`. §3.2.3.3, where a server publishes it, has `https://` for both, and §3.2.3.5 says non-secure HTTP URIs SHOULD NOT be used to query settings.) |
| §3.1.5.3 | The targets of the `_autodiscover._tcp.<domain>` SRV record (RFC 2782), `https://<host>/Autodiscover/Autodiscover.xml` | Taken, at the port the record gives when that is 443 or above 1023 |
| §3.1.5.4 | A plain-HTTP `GET` of `http://Autodiscover.<domain>/Autodiscover/Autodiscover.xml`: a 302 answer names another place, which is added once the user has been warned and accepts | **Not taken**: no connection that carries anything of the owner's is unencrypted, and an answer over plain HTTP can be written by anybody on the way. **The alias step takes its place** |

MS-OXDISCO §5.1: "There are many possible DNS spoofing attacks. For this reason, clients are
strongly advised against using non-SSL URIs unless they have the consent of the user."

## The alias step

### What it is for

A hosted Exchange server is commonly set up this way: the hosting provider runs one
Autodiscover server for all its customers, under its own name and with its own certificate.
Each customer points `autodiscover.<their domain>` at it with a DNS alias (a CNAME record,
RFC 1034 §3.6.2), and may publish an SRV record too:

```
autodiscover.example.org.        CNAME  autodiscover.de2.hoster.example.
_autodiscover._tcp.example.org.  SRV    0 0 443 autodiscover.de2.hoster.example.
```

MS-OXDISCO's second address, `https://autodiscover.example.org/…`, reaches the hoster's server
through the alias. The connection fails there, because the certificate names
`autodiscover.de2.hoster.example` and not `autodiscover.example.org`, as RFC 9525 says it must
(below). The SRV record names the hoster's host, which has the certificate. But many
organisations keep their SRV record only in the DNS of their own network (a split DNS), so a
computer that asks the public DNS, as MailCraft does over DNS-over-HTTPS, gets no SRV record. MS-OXDISCO's
way out is §3.1.5.4: the plain-HTTP `GET` to `autodiscover.example.org` reaches the hoster's
server through the same alias, and that server answers with a 302 to its own `https://` name.
MailCraft never takes that step. Without the alias step, such a domain's Exchange server is not
found at all, and the owner has to type its address.

The alias step finds the same server §3.1.5.4 would find, from the same alias. It differs in two
ways:

- The new place comes from a DNS answer over HTTPS from the resolver, not from a plain-HTTP
  answer from whoever is on the way.
- The owner is asked earlier than §3.1.5.4 asks.

### The rules

1. **The question.** The DNS is asked for the CNAME of `autodiscover.<domain>`, where `<domain>`
   is the mail domain of the address. It is asked of the same DNS-over-HTTPS resolvers, in the
   same way and at the same time as the SRV record (§3.1.5.3): only after the owner presses
   Connect, and with the domain alone (`mailcraft_net::autodiscover_targets`).
2. **The hosts taken.** A host from the answer is taken only when all of these hold:
   - it is a target of a CNAME record in the answer;
   - it is a plain host name;
   - its first label is `autodiscover`;
   - it is not `autodiscover.<domain>` itself.

   Anything else in the answer is passed over. A wildcard alias, which points every name in the
   domain at a web host, says nothing about Autodiscover. The search asks at most two hosts.
3. **The addresses.** Each host taken is asked at `https://<host>/autodiscover/autodiscover.xml`
   (port 443). A host the SRV record names at 443 is not asked twice. One it names at another port
   is asked at 443 as well, since that is another place.
4. **Their place in the list.** After the SRV record's targets and before the search ends. That
   is the place §3.1.5.4's redirect would take in MS-OXDISCO's order.
5. **HTTPS only.** The certificate is checked against `<host>`, the alias's host, by the system's
   verifier, as for every other address in the list. A certificate the system doesn't trust ends
   that place and nothing is sent over the connection, as for the others. The search offers no
   trust of its own: the owner can type the server's address in Server settings, where such a
   certificate is shown.
6. **The owner says yes first.** The alias is not trusted as the SRV record is. The owner is asked
   on a page that names the host whole and says how it was found: "Your domain's DNS points its
   autodiscover name at {host}, but doesn't name it in the record for Exchange's automatic setup.
   It may be a web host rather than your organisation's mail server." (`ConsentReason::Alias`).
   - **Outside the owner's mail domain:** before anything is sent to the host, the e-mail address
     included.
   - **Inside it:** the request with the address alone may go. The user name and password go only
     after the owner's yes, when the host asks for them.
   - **A no** sends nothing there, and the search goes on with the next place.

   This is §3.1.5.4's rule ("prompt the user to warn them of the redirection. If the user accepts,
   the new location is added to the list"), asked before the first request rather than after a
   redirect.
7. **After that,** the host is one more place in the list: its answer is read as MS-OXDSCLI
   §3.1.5 says, under the same rules as every other place (redirects one step at a time, at most
   five, to `https://` only; Exchange Online ends the search with the offer of a Microsoft
   account; the Exchange Web Services address the answer gives is asked about when it is outside
   the domain).

### Why a yes is needed

RFC 9525 §6.1.1 (service identity in TLS): a name met while the DNS is resolved "MUST NOT be
treated as" a reference identifier unless a process for authenticating it is defined. A name
the client checks the certificate against can be "(a) contained in or securely derived from the
inputs or (b) explicitly associated with the source domain by means of user configuration". The
alias's host is neither in the owner's input nor securely derived from it: the CNAME is a DNS
answer, and DNS-over-HTTPS protects the answer between the resolver and MailCraft, not where it
came from. So the owner's yes is the explicit association of (b). The connection then checks the
certificate against the host the owner agreed to. A forged or stale alias costs a question, never
the password.

### In Add Account

Add Account asks the same two DNS questions to tell, before anything is sent to any server,
whether an address at a domain nobody here knows is on an Exchange server
(`mailcraft_net::autodiscover_hosts`, `provider::by_autodiscover`). The alias's hosts are taken
there by rule 2 as well. They only choose the page that is shown, and none of them is asked
anything for it:

- Microsoft's: a Microsoft 365 account, signed in on Microsoft's page.
- cPanel's IMAP settings: IMAP.
- Any other: the owner is asked whether it is an Exchange server or IMAP, with neither answer the
  default.

IMAP, there and when the domain names no Autodiscover host, is the servers the domain's own SRV
records of RFC 6186 name (#1063), else the servers guessed from the domain, for the owner to
check.
